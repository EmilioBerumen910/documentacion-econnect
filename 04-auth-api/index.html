Autenticación y autorización

Estado actual

La autenticación del entorno actual es mixta e inconsistente.
Hay APIs con Cognito, otras con Lambda Authorizer configurado pero no aplicado y otras completamente abiertas.

Resumen por API

API Tipo Región Auth principal Riesgo
apieconnectpro REST us-east-1 Lambda Authorizer configurado pero no aplicado Alto
apiusuarios REST us-east-1 Cognito User Pools en la mayoría de métodos Medio
api_socket WebSocket us-east-2 NONE Alto
dev-auth-api HTTP us-east-2 NONE Alto

apieconnectpro

Authorizer configurado

  • Nombre: LambdaAutorizaApi
  • ID: 15qlr1
  • Tipo: REQUEST
  • Lambda target: AutorizadorApis
  • Caching TTL: 0

Problema crítico

Aunque existe authorizer, la evidencia indica que los métodos usan authorizationType = NONE.
En la práctica, eso significa que la API está expuesta sin autenticación efectiva.

Riesgos

  • falsa sensación de seguridad
  • exposición de endpoints sensibles
  • drift entre expectativa del equipo y comportamiento real

apiusuarios

Authorizer principal

  • Nombre: ApiAutorizador
  • Tipo: COGNITO_USER_POOLS
  • User Pool ID: us-east-1_s1zhiuODD
  • Región del User Pool: us-east-1

Observaciones

La mayoría de los métodos usan Cognito, pero hay excepciones con NONE, incluyendo: - OPTIONS - POST /create_notificacion - paths /s3 - algunos endpoints de tráfico - algunos endpoints de reportes y verificación

Riesgos

  • exposición parcial no intencional
  • inconsistencias entre rutas similares
  • frontends que parecen protegidos pero tienen bypass en endpoints específicos

Lambda Authorizer: AutorizadorApis

Detalles observados

  • Runtime: nodejs12.x
  • Timeout: 3 segundos
  • Memory: 128 MB
  • VPC config: no configurada
  • Permisos visibles: solo CloudWatch Logs

Implicaciones

  • runtime obsoleto
  • sin caching
  • timeout agresivo
  • si se habilita de verdad, podría introducir latencia o fallos

Cognito

Hallazgos confirmados

  • Se conoce el User Pool.
  • No hay evidencia de App Clients.
  • No hay evidencia de callback URLs, scopes ni TTLs de tokens.

Riesgo de migración

Cognito User Pools es regional.
Si la API migra de región, se debe decidir entre:

  1. mantener Cognito en us-east-1
  2. crear nuevo User Pool regional
  3. hacer transición gradual

Qué debe definirse antes de migrar

Política recomendada

Para cada API y método, definir una sola de estas opciones:

  • COGNITO_USER_POOLS
  • CUSTOM con Lambda Authorizer
  • JWT (si se moderniza HTTP API)
  • IAM
  • NONE solo cuando sea explícitamente público

Decisiones obligatorias

  • qué rutas deben ser públicas
  • qué rutas deben ser internas
  • qué rutas requieren token
  • si WebSocket debe autenticarse en $connect
  • si dev-auth-api seguirá existiendo como API pública

Diseño recomendado por tipo de API

REST críticas

  • usar Cognito o Lambda Authorizer aplicado realmente
  • remover NONE salvo endpoints públicos justificados
  • documentar excepciones una por una

WebSocket

  • autenticar en $connect
  • validar token o identidad antes de aceptar la conexión

HTTP API

  • preferir JWT/IAM cuando aplique
  • evitar exponer catch-all público con ANY /{proxy+}

Controles adicionales recomendados

  • tabla de autorización por método
  • pruebas automatizadas de endpoints públicos/protegidos
  • validación de OPTIONS sin filtrar rutas sensibles reales
  • revisión de authorizers obsoletos
  • modernización de runtimes

Resultado esperado post-migración

Una vez migrado, no debería existir: - API “aparentemente protegida” pero realmente abierta - rutas críticas con NONE por accidente - diferencias no documentadas entre stages
