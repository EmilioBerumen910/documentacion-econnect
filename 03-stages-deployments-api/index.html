Etapas y despliegues

Panorama

Los stages actuales son el principal mecanismo para diferenciar ambientes.
No hay evidencia de uso de Stage Variables, por lo que el cambio por ambiente parece depender de:

  • nombre de stage
  • deployment distinto
  • configuración en backend o código
  • mapeo de custom domains

Ausencia de Stage Variables

No se evidenciaron Stage Variables en los stages revisados.

Implicaciones

  • No existe mapeo por ambiente vía stage vars.
  • Cualquier cambio de endpoint, flag o backend probablemente depende del código o del deployment.
  • El drift entre ambientes puede pasar desapercibido si dos stages tienen deployment IDs distintos pero comportamiento similar solo en apariencia.

Versionado de stages

Los stages están vinculados a deploymentId, pero no hay trazabilidad clara a:

  • branch de Git
  • commit SHA
  • tag release
  • artefacto versionado

Evidencia de actividad

  • apieconnectpro: ~200 deployments
  • apiusuarios: 83 deployments
  • señales de automatización por Serverless Framework y Zappa
  • sin relación explícita a commits o releases

Riesgos operativos

1. Drift entre stages

Como no hay stage vars y cada stage puede apuntar a un deployment distinto, es posible que: - test - usuarios - econnect - valida
no representen configuraciones equivalentes ni trazables.

2. Ambigüedad de “producción”

Un hallazgo especialmente delicado es que el dominio api.econnectpro.mx está mapeado al stage test.
Eso obliga a confirmar si: - el stage test es realmente el ambiente productivo, o - existe una exposición accidental.

3. us-east-2 no listo

La presencia de APIs homónimas en us-east-2 sin stages activos indica que la región destino no está lista como reemplazo directo.

Qué debe documentarse por stage en la región destino

Para cada stage que vaya a existir en la nueva región:

  • nombre
  • deploymentId
  • auth por método
  • throttling
  • logging
  • tracing
  • métricas
  • CORS
  • dominio/mapping
  • fecha de creación
  • fecha de última actualización
  • runbook de rollback

Recomendación de migración

Opción recomendada

Crear stages explícitos y alineados con propósito real:

  • prod
  • test
  • valida
  • socket-prod o equivalente

Opción no recomendada

Repetir nombres históricos ambiguos sin redefinir semántica operativa.

Checklist previo a despliegue regional

  • [ ] Confirmar qué stage actual recibe tráfico real.
  • [ ] Confirmar qué deployment es la referencia funcional.
  • [ ] Confirmar si el stage mapeado al custom domain es intencional.
  • [ ] Versionar el despliegue con una convención reproducible.
  • [ ] Registrar una tabla “stage → deployment → artefacto → fecha”.
