Seguridad

Panorama

La superficie de seguridad actual de API Gateway depende demasiado de: - autenticación parcial o inconsistente - throttling global - backend - controles externos no evidenciados

No se observaron varios guardrails esperables para una plataforma expuesta públicamente.

WAF

Hallazgo

No hay evidencia de WAFv2 asociado a API Gateway ni a CloudFront para los dominios revisados.

Implicación

No existe una capa perimetral visible con: - managed rules OWASP - reputation lists - geo blocking - rate limiting administrado - inspección adicional en edge

Resource Policies

Hallazgo

No se observaron API Gateway Resource Policies en ninguna de las APIs revisadas.

Implicación

No hay restricciones por: - Source IP - VPC - VPC Endpoint - account - organization

Usage Plans y API Keys

Hallazgo

No hay Usage Plans y ningún endpoint evidenciado requiere API Key.

Implicación

No existe: - cuota por cliente - rate limit por cliente - aislamiento de consumidores por key

Throttling

Hallazgo

Hay throttling global en algunos stages, pero no en todos.

Configuración observada

  • burst: 5000
  • rate: 10000 RPS
  • aplicado vía methodSettings */* en algunos stages

Stages con throttling explícito

  • apieconnectpro stage test
  • apieconnectpro stage valida
  • apiusuarios stage test

Stages sin throttling explícito

  • apieconnectpro stage econnect
  • apiusuarios stage usuarios

Riesgo

Los límites son altos y además no son por cliente.
Un solo consumidor puede afectar al resto, y algunos stages ni siquiera tienen limitación explícita.

Rate limiting por cliente

Hallazgo

No existe rate limiting por cliente implementado vía API Gateway.

Lo que sí existe

  • throttling global por stage
  • auth por Cognito en algunos casos
  • posible control backend no evidenciado

Auth como guardrail

La seguridad actual depende en gran medida de auth, pero auth no es uniforme:

  • apieconnectpro: authorizer configurado pero no aplicado
  • apiusuarios: mezcla Cognito con endpoints NONE
  • api_socket y dev-auth-api: abiertos según evidencia

Esto reduce la efectividad del diseño de seguridad.

Riesgos principales

1. API pública con controles parciales

Especialmente delicado en apieconnectpro.

2. Ausencia de perímetro fuerte

Sin WAF ni resource policies.

3. Sin consumo por cliente

No hay aislamiento por tenant o consumidor.

4. Exposición por rutas binarias / archivos

Si se combinan rutas tipo /s3 o /uploads3 con auth parcial, CORS permisivo y binarios, el riesgo sube.

Objetivo de seguridad para la región destino

Recomendado

  1. Definir auth por método.
  2. Revisar si se requiere WAF.
  3. Evaluar resource policies para APIs no públicas o restringidas.
  4. Normalizar throttling por stage.
  5. Implementar rate limits por cliente si existen consumidores diferenciados.
  6. Revisar endpoints abiertos y justificar cada uno.

Controles mínimos recomendados

Perímetro

  • WAF para api.econnectpro.mx
  • evaluación de WAF o controles equivalentes para front doors críticos

API Gateway

  • resource policies si aplica restricción por IP o VPCe
  • throttling consistente en todos los stages críticos
  • auth homogénea
  • reducción de NONE a solo endpoints explícitamente públicos

Identidad

  • Cognito o authorizer real aplicado
  • revisión de tokens, scopes y expiración
  • autenticación de $connect en WebSocket

Operación

  • logs
  • alarmas
  • runbook de abuso / anomalía
  • evidencias de quién cambia domain mappings y stages

Matriz recomendada de exposición

API / Ruta Pública Requiere token Requiere WAF Requiere rate limit Observaciones

Esta matriz debe existir antes del cutover.
