Plan de migración

Objetivo

Migrar el servicio API Gateway a la región destino con un proceso:

  • controlado
  • observable
  • reversible
  • compatible con dominios existentes
  • alineado a dependencias reales

Principios de ejecución

  1. No mover tráfico antes de recrear integraciones y auth.
  2. No considerar “lista” una API solo porque exista en otra región.
  3. Usar domain mappings como mecanismo principal de cutover.
  4. Preparar rollback antes del cambio.
  5. Validar APIs con clientes reales, no solo con curl.

Riesgos de partida

  • us-east-2 no tiene todas las APIs listas para producción.
  • apieconnectpro y apiusuarios aparecen sin stages activos en esa región.
  • auth es inconsistente.
  • observabilidad es limitada.
  • CORS y binarios pueden romper clientes.
  • no hay CI/CD formal ni trazabilidad fuerte por commit/tag.
  • dependencias a api.power-devel.com y Lambdas cross-region siguen vigentes.

Fases de migración

Fase 0 — Preparación

Entregables

  • matriz completa de APIs, stages, rutas e integraciones
  • tabla de dominios y mappings actuales
  • tabla de auth por método
  • tabla de CORS y binarios
  • runbook de rollback
  • dashboard mínimo y alarmas mínimas

Checklist

  • [ ] Confirmar API IDs finales.
  • [ ] Confirmar stages realmente productivos.
  • [ ] Confirmar dependencias cross-region.
  • [ ] Confirmar certificados y dominios.
  • [ ] Confirmar qué backends siguen en us-east-1.
  • [ ] Confirmar si Cognito se mantiene o se replica.

Fase 1 — Recreación técnica en región destino

Crear / recrear

  • APIs REST/HTTP/WebSocket necesarias
  • rutas y métodos
  • integraciones Lambda / HTTP_PROXY / MOCK
  • permisos lambda:InvokeFunction
  • custom domains
  • certificados necesarios
  • mappings
  • OPTIONS y Gateway Responses
  • binary media types
  • auth y authorizers
  • throttling
  • logging y métricas

Criterio de salida

La nueva región debe responder funcionalmente sin recibir tráfico productivo.

Fase 2 — Hardening previo

Seguridad

  • aplicar auth real donde corresponda
  • revisar rutas NONE
  • definir WAF / resource policies si aplica
  • normalizar throttling

Observabilidad

  • access logs
  • execution logs
  • alarmas
  • dashboard de migración

Criterio de salida

La región destino debe ser operable, no solo funcional.

Fase 3 — Pruebas integrales

Pruebas obligatorias

REST

  • GET/POST/PUT/DELETE principales
  • rutas ANY y {proxy+}
  • respuestas 200, 4XX y 5XX
  • auth correcta
  • headers correctos

Web

  • preflight OPTIONS
  • CORS en errores
  • clientes browser reales

Binarios

  • upload multipart
  • download octet-stream
  • validación de integridad
  • tamaños límite

WebSocket

  • $connect
  • $disconnect
  • $default
  • autenticación si aplica
  • reintentos y errores

Dependencias

  • Lambda
  • api.power-devel.com
  • S3
  • SQS
  • cualquier backend externo relevante

Criterio de salida

La región destino debe pasar pruebas comparables a la región actual.

Fase 4 — Cutover controlado

Estrategia recomendada

Cambiar el custom domain mapping del dominio hacia la API/stage destino.

Motivo

Es el mecanismo más alineado con la arquitectura observada y el más reversible.

Orden sugerido

  1. APIs no críticas o de menor blast radius.
  2. socket.econnectpro.mx si el canal de tiempo real puede aislarse.
  3. api.econnectpro.mx al final, cuando todo esté validado.

Durante el cutover

  • monitorear 4XX/5XX
  • monitorear latencia
  • revisar logs Lambda
  • probar endpoints críticos
  • validar handshake WebSocket
  • validar uploads y descargas

Fase 5 — Estabilización

Ventana inmediata post-cambio

  • revisar errores por 15 min, 30 min, 60 min
  • revisar métricas y logs
  • validar rutas críticas con usuarios o sistemas reales
  • revisar auth
  • revisar dominios y TLS

Rollback

Estrategia recomendada

Revertir el custom domain mapping al target anterior.

Datos que deben quedar guardados antes del cambio

  • dominio
  • endpoint type
  • API ID anterior
  • stage anterior
  • target anterior
  • timestamp de cambio
  • responsable del cambio

Cuándo hacer rollback

  • aumento sostenido de 5XX
  • rutas críticas no funcionales
  • auth fallando
  • clientes browser rompiéndose por CORS
  • uploads binarios corruptos
  • degradación significativa de latencia
  • fallos WebSocket generalizados

Tiempo objetivo

  • rollback por mapping: inmediato / < 30 s
  • rollback por DNS: solo como último recurso

Validación posterior al rollback

  • confirmar mapping restaurado
  • re-probar endpoints críticos
  • registrar incidente y causa

Recomendaciones estructurales posteriores

Una vez terminada la migración, conviene cerrar deuda técnica:

  • unificar IaC
  • crear pipeline reproducible
  • vincular deployments a commits/tags
  • endurecer auth
  • implementar guardrails de seguridad
  • mejorar observabilidad
  • eliminar dependencias cross-region cuando ya no sean necesarias

Criterio de éxito

La migración será exitosa cuando:

  • los dominios sigan operativos
  • las rutas críticas respondan correctamente
  • auth sea consistente
  • clientes web no fallen por CORS
  • binarios no se corrompan
  • exista rollback probado
  • el entorno destino sea más observable y gobernable que el actual
