CORS y manejo de binarios

Panorama

La configuración CORS actual es funcional en varias APIs, pero no homogénea entre regiones.
Además, existen configuraciones de binarios y CONVERT_TO_TEXT que pueden romper clientes web o flujos de archivos durante la migración.

CORS por API

us-east-1

apieconnectpro

  • CORS implementado con MOCK OPTIONS
  • Access-Control-Allow-Origin: *
  • Access-Control-Allow-Methods: DELETE,GET,HEAD,OPTIONS,PATCH,POST,PUT
  • Access-Control-Allow-Headers: Content-Type,X-Amz-Date,Authorization,X-Api-Key,X-Amz-Security-Token
  • conclusión: correcto y permisivo

apiusuarios

  • MOCK OPTIONS extensivo
  • Access-Control-Allow-Origin: *
  • métodos permitidos completos, con algunos casos específicos POST,OPTIONS
  • conclusión: correcto

quicksight

  • CORS específico para:
  • OPTIONS
  • POST
  • integración non-proxy con response mapping explícito
  • conclusión: correcto pero más frágil

api_socket

  • al ser WebSocket, CORS no aplica igual que en REST
  • el handshake inicial se maneja a nivel cliente/aplicación

us-east-2

apiusuarios

  • CORS completo
  • Gateway Responses con CORS en errores
  • conclusión: robusto

api_procontrol

  • solo Gateway Responses
  • sin OPTIONS en recursos
  • conclusión: restringido / problemático

apieconnectpro

  • OPTIONS en recursos sí
  • Gateway Responses sin CORS en errores
  • conclusión: parcial

Riesgos CORS

1. Origen wildcard

El uso de * simplifica compatibilidad, pero no endurece seguridad.

2. Errores sin CORS

Si 4XX/5XX no devuelven headers CORS, los navegadores fallarán aunque el backend responda.

3. Diferencia entre regiones

Si una región responde bien y la otra no, el cutover puede romper clientes web sin cambiar el contrato funcional del backend.

Binary Media Types

Evidencia confirmada

Se observan tipos binarios configurados, al menos: - multipart/form-data - application/octet-stream

APIs con evidencia de binarios

  • apiusuarios en us-east-2

Lambda relacionada

  • insertaMensajeSQSArchivosS3

Content Handling: riesgo principal

La evidencia muestra Content Handling = CONVERT_TO_TEXT en varias integraciones.
Eso es especialmente delicado para payloads binarios.

Riesgos

  • corrupción de archivos
  • expansión base64 (~33%)
  • reducción del tamaño útil
  • fallos de cliente por límites efectivos menores
  • diferencias entre respuesta backend y respuesta pública

Límites relevantes

Límite Valor
payload request/response REST 10 MB
payload request/response HTTP API 10 MB
headers combinados REST 10,240 bytes
mapping templates 300 KB
integration timeout efectivo ~29 segundos

Implicación práctica

Aunque Lambda permita timeouts mayores, el cliente verá timeout en torno a 29 segundos si entra por API Gateway.

Riesgos por API

apieconnectpro us-east-1

  • binarios habilitados
  • CONVERT_TO_TEXT
  • flujos de archivo observados
  • riesgo alto de rotura si no se replica igual o si se corrige sin pruebas

apiusuarios us-east-1

  • HTTP_PROXY a backend externo
  • uploads observados
  • dependencia externa puede modificar headers o timeouts

apieconnectpro us-east-2

  • cross-region a Lambdas en us-east-1
  • CONVERT_TO_TEXT
  • binarios extensivos
  • región especialmente riesgosa

Qué debe validarse post-migración

Navegador

  • preflight OPTIONS
  • respuestas 200, 4XX y 5XX con CORS correcto
  • uploads desde frontend real

API clients

  • envío multipart
  • descarga octet-stream
  • preservación de Content-Type
  • preservación de Content-Disposition

Archivos

  • tamaño
  • integridad
  • encoding
  • tiempos de subida
  • manejo de errores

Recomendación técnica

  • estandarizar Gateway Responses con CORS
  • revisar cada uso de CONVERT_TO_TEXT
  • documentar explícitamente qué rutas son binarias
  • separar flujos JSON de flujos binarios
  • probar con archivos reales antes del cutover
