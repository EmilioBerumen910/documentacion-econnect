Provisioning de EC2 (cómo se “arma” la plataforma)

Fuente: assets/EC2-Documentacion-Econnect.pdf
Generado: 2026-03-03

Método de creación por componente

  • MongoDB (Primary/Secondary/Replica Nodes): CloudFormation ✅
  • Athena connectors (MySQL/DocumentDB): CloudFormation (Serverless Repo) ✅
  • Zappa (task-dev / zappatest-dev): Zappa (stacks CloudFormation) ✅
  • SOLUCIONA31 (EC2): existe Launch Template pero sin ASG ⇒ lanzamiento manual desde template / legacy ✅
  • Resto de apps detrás de ALB (econnect/admin/reportes/integra24/apivucem/apiSA31): con la evidencia disponible no aparecen como ASG ni como stacks ⇒ probable creación manual.

Nota: varias AMIs Windows aparecen como deleted/private (no visibles). Para migración es importante identificar el mecanismo real de build/actualización (golden AMI, snapshots, o reinstalación).

Tipos de instancia (racional observado)

  • win_robots — t2.medium: burstable (workloads intermitentes). Verificar CPUCreditBalance.
  • Mongo-Primary — r5a.4xlarge: memory optimized (MongoDB suele necesitar RAM alta).
  • Mongo-Reports — r5a.2xlarge: memory optimized (reporting/consultas).
  • sa31 c6 — c6in.8xlarge: compute optimized + red alta (carga CPU/network).

Almacenamiento (EBS) y respaldos

  • Volúmenes EBS: gp3 (mayoría), io1 (4 vols de 25 GiB), gp2 (1 vol de 400 GiB).
  • Snapshots/AMIs: se observan como práctica de recovery manual.
  • No se detecta DLM (Data Lifecycle Manager) como política central.

Implicación operativa: el recovery depende de disciplina manual (AMIs/snapshots puntuales) más que de una política automatizada.
