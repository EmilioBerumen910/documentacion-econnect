Qué envía el agent (observado): - Métricas de sistema (Windows: disk/mem; Linux: mem/disk)

Qué no queda claro: - Envío de logs de aplicación desde EC2 (Nginx/app/Mongo/etc.)

CloudWatch Logs (log groups)

  • us-east-1: 90+ log groups; alto volumen en vpc_flowlog (~38.7 GB) y muchos log groups de Lambda (procesos PDF/XML/etc.)
  • us-east-2: ~10 log groups (principalmente Lambda y Glue)

Fuentes identificadas: - VPC Flow Logs ✅ - Lambda ✅ - Glue ✅ - API Gateway ✅/⚠ (verificar) - EC2 app logs ❌ (limitados/no detectados)

Alarmas (CloudWatch)

Inventario observado: - Total: 12 alarmas (todas en us-east-1) - Acciones: notifican a Default_CloudWatch_Alarms_Topic

EC2

  • CPU (4): threshold ≥ 85% (5 min / 1 datapoint)
  • Memoria (4): threshold ≥ 85% (5 min / 1 datapoint)
  • Disco (4+): ~85% used o ≤15% free (Windows Free Space)

Estado reportado: 4 en ALARM (3 disco Windows + 1 memoria en win_robots); resto OK.

Gaps críticos de monitoreo

  • No hay alarmas de ALB (5xx/latency/UnHealthyHostCount).
  • No hay alarmas de RDS (CPU, FreeStorageSpace, FreeableMemory, Connections, etc.).
  • No hay alarmas de SQS (AgeOfOldestMessage, DLQ, etc.).
  • No hay alarmas de Lambda (Errors/Throttles/Duration).
  • us-east-2 sin alarmas.

Recomendaciones operativas (para cerrar gaps)

  1. Agregar alarmas mínimas para RDS (storage/memory/connections).
  2. Agregar alarmas para ALB (5xx, latency, UnHealthyHostCount).
  3. Agregar alarmas para SQS (AgeOfOldestMessage + DLQ).
  4. Agregar alarmas para Lambda (Errors/Throttles/Duration).
  5. Estandarizar envío de logs de aplicación desde EC2 (CloudWatch Logs o pipeline alterno).
