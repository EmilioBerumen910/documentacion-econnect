Logging y monitoreo

Estado actual de observabilidad

La observabilidad de API Gateway es débil.
La evidencia apunta a un entorno con muy poca instrumentación nativa del servicio, lo que incrementa el riesgo de una migración sin visibilidad suficiente.

Access logs

Hallazgo

No hay evidencia de Access Logs habilitados en los stages REST principales de us-east-1.

Implicación

Sin access logs no se puede observar fácilmente: - IP origen - status code - latencia - user agent - path consumido - volumen por stage - errores CORS o auth

Execution logs

Hallazgo

Los Execution Logs están efectivamente deshabilitados en los stages revisados.

Causa adicional

No está configurado el CloudWatch Logs Role ARN a nivel cuenta para API Gateway en us-east-1.

Implicación

Aunque se quisiera activar logging, primero debe resolverse la configuración de cuenta.

X-Ray

Estado

Solo se observó X-Ray habilitado parcialmente: - apieconnectpro stage valida → tracingEnabled = true

No habilitado en

  • apieconnectpro stage test
  • apieconnectpro stage econnect
  • apiusuarios stages test y usuarios

Implicación

La trazabilidad actual es inconsistente y no sirve como base uniforme para comparar ambientes.

Métricas

Hallazgo

No hay métricas detalladas por método/recurso activadas (metricsEnabled = false), pero sí hay alguna evidencia de métricas básicas por API/stage.

Ejemplo

  • apieconnectpro stage test tiene datapoints básicos
  • apiusuarios no muestra datapoints visibles en la evidencia consultada

Alarmas

Hallazgo

No hay CloudWatch Alarms de API Gateway para: - 4XXError - 5XXError - Latency - IntegrationLatency

Implicación

No existe alerta temprana específica del plano API durante una degradación.

Dashboards

Hallazgo

Existen dashboards llamados Econnect, pero están vacíos o no útiles para validación post-migración.

Implicación

No hay panel operativo que permita decidir rápidamente: - go / no-go - rollback - impacto por endpoint

Problemas derivados para migración

1. Cutover sin visibilidad

Mover tráfico sin logs ni alarmas deja al equipo operando “a ciegas”.

2. Troubleshooting lento

Será difícil diferenciar si un fallo viene de: - API Gateway - Lambda - backend HTTP externo - auth - CORS - DNS / domain mapping

3. Sin baseline

No existe una línea base operacional confiable para comparar el “antes” vs “después”.

Recomendación mínima antes del cutover

Habilitar Access Logs

Definir un formato con al menos: - requestId - ip - requestTime - httpMethod - resourcePath / routeKey - status - protocol - responseLength - integrationErrorMessage

Habilitar Execution Logs

  • nivel mínimo: ERROR
  • usar INFO temporalmente durante ventana de migración si el costo lo permite

Habilitar métricas

  • métricas básicas por API/stage como mínimo
  • métricas detalladas en APIs críticas si el costo y el volumen lo justifican

Crear alarmas

Recomendadas

  • 5XX > umbral
  • 4XX anómalo
  • Latency p95 alta
  • IntegrationLatency alta
  • Count anómalo
  • error de Lambda target

Crear dashboard de migración

Widgets mínimos: - Requests - 4XX - 5XX - Latency - IntegrationLatency - Lambda errors - Lambda duration - WebSocket connect/disconnect si aplica

Validación post-migración

Durante la ventana de cambio, revisar por intervalos cortos:

  1. tráfico total
  2. errores 4XX
  3. errores 5XX
  4. latencia media y p95
  5. errores de integración
  6. logs del authorizer y Lambdas críticas
  7. handshake WebSocket

Resultado esperado

El estado objetivo post-migración no debe ser solo “la API responde”.
Debe existir al menos:

  • logs por stage
  • métricas básicas
  • alarmas de API Gateway
  • dashboard operativo
  • runbook de rollback vinculado a señales medibles
