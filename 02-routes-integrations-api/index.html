Integraciones

Objetivo

Esta sección documenta qué rutas existen, a qué backend apuntan y qué dependencias deben recrearse para que la migración sea funcional.

Patrón dominante de integración

La plataforma usa principalmente tres patrones:

  1. AWS_PROXY → Lambda
  2. HTTP/HTTP_PROXY → backend externo
  3. MOCK → OPTIONS / CORS

No hay evidencia de: - VPC_LINK - integraciones con ALB/NLB vía API Gateway - Step Functions expuestas por API Gateway en la evidencia revisada

Riesgos de integración

1. Dependencia fuerte de Lambda

La mayor parte del comportamiento depende de Lambdas.
Cualquier límite de memoria, timeout, permisos o concurrencia impacta directamente la API.

2. Blast radius por ANY + {proxy+}

Varias rutas concentran lógica en pocos handlers, lo que aumenta el radio de impacto ante errores.

3. Dependencia externa por HTTP_PROXY

api.power-devel.com introduce riesgo adicional: - SLA desconocido - timeout desconocido - drift fuera del control de API Gateway - posible dependencia cross-region o fuera del plan de migración

4. Integraciones cross-region

En us-east-2 hay evidencia de APIs que integran con Lambdas en us-east-1.
Eso significa que “migrar el front door” sin migrar los backends solo movería el problema, no la arquitectura.

Qué debe recrearse exactamente en la región destino

Para cada API deben portarse:

  • rutas y métodos
  • tipo de integración
  • target backend exacto
  • permisos lambda:InvokeFunction
  • OPTIONS y configuraciones CORS
  • templates y response mappings
  • binary media types
  • auth por método
  • gateway responses personalizadas

Recomendación de trabajo
