Target Groups: puertos y health checks

Configuración estándar observada de health check: - Protocol: HTTP - Port: traffic port - Path: / - Success codes: 200 - Interval: 30s - Timeout: 5s - Healthy threshold: 5 - Unhealthy threshold: 2

Puertos por target group (según inventario): - admin: 8888 - apireportes: 8880 - apivucem: 8881 - ds1: 8885 - integra24: 80 - rabit: 15672 - sa31Pro: 8882 - soluciona31: 8889

Nota operativa: con matcher solo 200 y path /, una app que responda 301/302/401/403/204 en / puede quedar “unhealthy”. Si hay flapping, primer ajuste típico: success codes 200-399 o un path /health.

DNS (Route 53)

  • Hosted Zone pública: econnectpro.mx.
  • Routing observado: A/ALIAS (hacia CloudFront y algunos ALBs dualstack) y CNAME (hacia DNS públicos de EC2 u otros destinos).

CloudFront (CDN)

Se observan 2 distribuciones CloudFront (enabled): - Distribución para econnectpro.mx y www.econnectpro.mx → origin S3: econnectpro.mx.s3.amazonaws.com - Distribución para login.econnectpro.mx → origin S3 Static Website: login.econnectpro.mx.s3-website-us-east-1.amazonaws.com

WAF

  • No hay WAF habilitado en CloudFront (Core protections = Not enabled).

Implicación: apps expuestas carecen de una capa gestionada de protección web (OWASP rulesets, rate limiting, etc.).
