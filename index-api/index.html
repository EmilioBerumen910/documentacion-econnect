API Gateway — Inicio

Propósito

Esta documentación describe el estado actual del servicio API Gateway de la plataforma Econnect y define los elementos que deben recrearse o ajustarse durante una migración regional.
El documento es independiente y está enfocado en inventario, dependencias, seguridad, observabilidad y ejecución del cutover.

Resumen ejecutivo

El inventario analizado muestra un ecosistema API Gateway distribuido principalmente entre us-east-1 y us-east-2, con predominio de REST APIs, presencia de WebSocket APIs y al menos una HTTP API.
En us-east-1 se concentran las APIs activas y los custom domains principales; en us-east-2 existen APIs parciales, de soporte o sin stages activos.

Hallazgos principales

  • En us-east-1 existen 4 APIs activas visibles:
  • apiusuarios — REST
  • quicksight — REST
  • apieconnectpro — REST
  • api_socket — WebSocket
  • Los custom domains identificados son:
  • api.econnectpro.mx
  • socket.econnectpro.mx
  • La arquitectura actual depende en gran medida de:
  • Lambda / AWS_PROXY
  • HTTP_PROXY hacia api.power-devel.com
  • MOCK para OPTIONS y CORS
  • No hay evidencia de:
  • VPC Link
  • Usage Plans
  • API Keys obligatorias
  • Resource Policies
  • WAF
  • pipelines CI/CD formales
  • La observabilidad es limitada:
  • sin access logs
  • sin execution logs
  • sin alarmas de API Gateway
  • con X-Ray parcial
  • Existen riesgos de seguridad y operación:
  • métodos con authorizationType = NONE
  • CORS inconsistente entre regiones
  • CONVERT_TO_TEXT en rutas con binarios
  • stages sin throttling explícito
  • configuraciones fragmentadas entre regiones

Supuestos de este documento

  • La región operativa principal actual es us-east-1.
  • us-east-2 contiene piezas de soporte, pruebas o preparación, pero no refleja un reemplazo listo para producción de todas las APIs.
  • La mayor parte del tráfico crítico parece estar concentrada en apieconnectpro, apiusuarios y api_socket.
  • Donde la evidencia no confirma un detalle, se marca explícitamente como no evidenciado o inferido.

Objetivo de migración

El objetivo no es solo “levantar APIs” en otra región.
El objetivo es recrear una plataforma API funcional, segura, observable y reversible, asegurando:

  • continuidad de integraciones
  • compatibilidad con clientes web y de tiempo real
  • preservación de dominios
  • rollback rápido
  • reducción de drift entre ambientes y regiones
